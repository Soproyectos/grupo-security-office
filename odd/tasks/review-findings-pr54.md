# Gentle AI review findings (PR #54, lineage review-999c7817c7782239) - non-blocking follow-ups

## R1-ip-hash-reversible [WARNING] src/backend/src/modules/access-requests/access-requests.service.ts:21-24
hashIp() computes an unsalted SHA-256 of the raw client IP (crypto.createHash('sha256').update(ipAddress).digest('hex')) before storing it as AccessRequest.ipHash. IPv4 address space is only ~4.3 billion values, so an unsalted hash is trivially reversible by brute force or a precomputed rainbow table, giving no real protection over storing the IP in cleartext. This directly contradicts the privacy guarantee asserted in the accompanying Prisma model comment ('ipHash es sha256 del IP cliente (nunca se almacena IP en claro)'), so anyone with read access to the access_requests table (e.g. a DB dump, backup, or compromised staff credential) can recover the exact submitter IP despite the code's stated intent to anonymize it.

## R1-trust-proxy-unconditional [SUGGESTION] src/backend/src/main.ts:17-19
app.set('trust proxy', 1) unconditionally trusts one hop of client-supplied X-Forwarded-For/X-Real-IP headers so Express (and therefore req.ip used both for ThrottlerGuard and for the ipHash input) will use attacker-controllable header values whenever the deployment topology has more or fewer than exactly one trusted reverse proxy in front of the app (e.g. an additional CDN/load balancer, or the service ever being reachable without the assumed nginx hop). If that assumption doesn't hold, the 5-requests/10-minutes public throttle on POST /api/public/access-requests becomes bypassable by varying the forwarded-for header per request. This is conditional on infrastructure not visible in this diff, so it is reported as a configuration risk to verify rather than a proven exploit.

## R4-001 [WARNING] src/backend/src/modules/access-requests/access-requests.service.ts:113-126
updateStatus() calls prisma.accessRequest.update() with no try/catch. If a staff member acts on an id that no longer matches a row (already processed by another staffer, deleted, or a stale id from a cached list), Prisma throws PrismaClientKnownRequestError P2025 (record not found), which is unhandled here and propagates as a generic 500 Internal Server Error via Nest's default filter instead of a clean 404/409. The new spec file only tests the happy path for updateStatus and has no not-found test, so this failure mode ships without coverage.

## R4-002 [SUGGESTION] src/backend/src/modules/access-requests/access-requests.service.ts:78-107
findAll() forwards the raw `status` query string into a Prisma `where` clause via `status as any` with no whitelist/enum check in the service or in the controller's `@Query('status') status?: string`. An out-of-enum value (typo, future filter UI bug, manual query param) will fail at the Postgres enum-type boundary and surface as an unhandled 500 on this staff-facing listing endpoint rather than a validated 400.

## R4-003 [SUGGESTION] src/backend/src/modules/access-requests/access-requests.service.ts:36-72
createPublic() performs a single non-idempotent insert with no idempotency key, and the AccessRequest model backing it (schema.prisma) has ordinary lookup indexes on email/nit but no unique constraint. A public lead-capture form is a classic retry-prone client (mobile network, form re-submission after a perceived timeout); combined with the frontend's manual retry path (RequestAccess.tsx re-invokes submitAccessRequest on any subsequent submit attempt), a legitimate retry after an ambiguous network failure will silently create a duplicate lead row with no server-side dedication or detection.

## R4-004 [SUGGESTION] src/backend/src/modules/access-requests/access-requests.service.ts:63-67
The catch block for the public create path logs only `error.code || error.message` with no request/correlation identifier and no stack trace. This is a deliberate PII-avoidance choice, but it also means an on-call engineer diagnosing a spike of 500s from the public access-request endpoint (e.g., DB connection exhaustion vs. constraint violation) has to correlate by timestamp alone, since nothing here ties the log line back to a specific request.

## R3-response-shape-mismatch [WARNING] src/frontend/src/services/access-requests.service.ts:13-23
The frontend declares `AccessRequestResponse` with fields id/companyName/nit/contactName/email/phone/customerType/status/createdAt and types `submitAccessRequest`'s return as that shape, but the actual backend endpoint it calls (`POST /public/access-requests`) always resolves with `{ received: boolean }` per AccessRequestsService.createPublic, and the controller's own Swagger example even shows a differently-shaped `{ data: { received: true } }` envelope. ## R3-findall-status-unvalidated [WARNING] src/backend/src/modules/access-requests/access-requests.service.ts:89
The staff `findAll` endpoint accepts an arbitrary `status` query string and passes it straight into a Prisma `where` clause via `status as any` with no enum validation in the controller or DTO. An invalid status value (anything other than PENDING/APPROVED/REJECTED) will cause Prisma to throw at query time rather than return a clean 400. No test in access-requests.service.spec.ts exercises an invalid/unexpected status value, so this input-boundary behavior is unproven.

## R3-updatestatus-notfound-unhandled [WARNING] src/backend/src/modules/access-requests/access-requests.service.ts:113-126
`updateStatus` calls `prisma.accessRequest.update({ where: { id }, ... })` directly with no try/catch and no existence check. `ParseUUIDPipe` on the controller only validates UUID format, not that a row exists, so a well-formed but non-existent id will make Prisma throw a 'record not found' error that is not mapped to a NotFoundException; the resulting response code/shape for this case is unproven, and access-requests.service.spec.ts only tests the happy-path update.
